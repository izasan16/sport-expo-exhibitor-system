# 中国国际体育用品博览会展商系统技术方案

## 1. 技术方案目标

本技术方案面向真实可落地的生产系统，支撑展商从报名、面积购买、合同签署、付款确认、展位选择、后台审核、服务办理到数据归档的完整业务闭环。

技术方案必须满足以下硬性要求：

- 前端使用 React + TypeScript。
- 页面设计严格遵守 Ant Design 设计规范。
- 前端组件必须使用 Ant Design 和 ProComponents。
- 后端使用 Java Spring Boot。
- 数据库使用 PostgreSQL，由采购方提供并交付 JDBC 连接信息；应用方不申请新建数据库实例，而是在采购方提供的 PostgreSQL 实例内申请独立 schema（默认命名 exhibitor_sys）部署全部业务表。
- 缓存、草稿 TTL、辅助锁和热点数据使用 Redis。
- 文件存储通过统一文件服务抽象，底层可对接对象存储或本地文件服务。
- 定时任务由后端调度执行。
- 部署形态为 Nginx + Spring Boot 后端服务 + PostgreSQL + Redis。
- 不进行历史数据迁移，新系统从空白启动。

## 2. 总体架构

### 2.1 架构形态

系统采用前后端分离、后端模块化单体架构。

```text
浏览器
-> Nginx
-> React + TypeScript + Ant Design 前端静态资源
-> Spring Boot REST API
-> PostgreSQL
-> Redis
-> 文件存储
```

后台管理端和展商端共用一套前端工程，通过路由、菜单、权限和布局区分不同入口。前端必须按路由级 code-splitting 和懒加载拆分后台端与展商端代码，避免展商端首屏加载后台管理页面代码。

后端不拆微服务，采用模块化单体。这样可以降低分布式事务、跨服务调用和部署复杂度，更适合订单、合同、付款、展位锁定等强一致业务。

### 2.2 技术栈

| 层级 | 技术选型 | 说明 |
| --- | --- | --- |
| 前端框架 | React + TypeScript | 保障类型安全和组件化开发 |
| UI 规范 | Ant Design | 页面设计和交互规范的唯一标准 |
| UI 组件 | Ant Design + ProComponents | 表格、表单、布局、详情、审核等组件统一使用 |
| 后端框架 | Java Spring Boot | 承载业务 API、事务、权限、定时任务 |
| 数据库 | PostgreSQL | 业务主库，保存最终业务状态 |
| 缓存/辅助锁 | Redis | 草稿 TTL、验证码、缓存、辅助锁 |
| 文件存储 | 文件服务抽象 | 可接对象存储或本地文件系统 |
| 网关/静态资源 | Nginx | 前端资源托管和 API 反向代理 |

### 2.3 核心设计原则

- PostgreSQL 是最终业务状态来源。
- Redis 不作为最终一致性依据，只用于缓存、TTL、辅助锁和临时数据。
- 展位正式锁定和确认必须通过 PostgreSQL 事务和行级锁保证。
- 所有关键状态变更必须经过后端服务层。
- 财务、合同、展位、审核相关操作必须写审计日志。
- 页面、交互、组件和视觉状态必须遵守 Ant Design 规范。

## 3. 前端技术方案

### 3.1 前端工程

前端采用 React + TypeScript + Ant Design + ProComponents。

建议工程能力：

- React Router 管理展商端和后台端路由。
- Ant Design ConfigProvider 统一主题、语言、组件尺寸和表单校验文案。
- ProLayout 承载后台管理布局。
- 权限路由根据登录用户角色和菜单权限动态生成。
- API 请求统一封装，处理 token、错误提示、分页参数和下载。
- 状态字典、枚举和权限点集中管理。

### 3.2 Ant Design 使用规范

页面设计必须严格遵守 Ant Design 规范。除业务需要的少量布局样式外，不自造基础组件。

组件使用要求：

| 场景 | 组件 |
| --- | --- |
| 后台整体布局 | ProLayout |
| 数据表格 | ProTable |
| 查询筛选 | ProTable search、ProForm |
| 新增/编辑表单 | ProForm、ModalForm、DrawerForm |
| 详情展示 | Descriptions、Card、Tabs |
| 流程进度 | Steps、Timeline |
| 审核操作 | Modal + Form |
| 状态展示 | Tag、Badge、Result |
| 上传文件 | Upload |

| 数字金额 | InputNumber、Statistic |
| 操作确认 | Popconfirm、Modal.confirm |
| 消息反馈 | message、notification |

禁止事项：

- 不自造按钮、表格、分页、弹窗、日期选择器、上传组件。
- 不使用与 Ant Design 视觉冲突的自定义控件。
- 不通过大面积自定义 CSS 改写 Ant Design 交互行为。
- 不把后台系统做成营销落地页风格。

### 3.3 页面布局规范

后台管理端采用工作台式布局：

- 顶部显示系统名称、当前展会、用户信息、消息入口。
- 左侧菜单按业务域组织。
- 内容区使用 Ant Design 的 PageContainer、ProCard、ProTable、Tabs 等组件。
- 表格页采用“查询区 + 表格 + 批量操作 + 行操作”的标准形态。
- 详情页采用“基础信息 + 状态流转 + 关联数据 + 操作日志”的结构。

展商端采用简化业务办理布局：

- 首页展示报名、合同、付款、选位、服务办理进度。
- 每个流程节点使用 Steps 展示当前进度。
- 表单尽量分段，避免长页面一次性填写过多内容。
- 状态变化使用 Tag、Alert、Result 明确提示。

## 4. 后端技术方案

### 4.1 后端架构

后端采用 Spring Boot 模块化单体架构。

建议分层：

```text
controller
-> application service
-> domain service
-> repository / mapper
-> PostgreSQL / Redis / file storage
```

分层职责：

- Controller 负责参数校验、鉴权入口和响应封装。
- Application Service 编排业务流程和事务边界。
- Domain Service 承载订单、付款、选位、展位状态机等核心业务规则。
- Repository/Mapper 负责数据访问。
- Scheduler 负责超时释放、草稿清理、通知补偿等定时任务。

### 4.2 后端模块

```text
auth 权限认证
system 系统管理
event 展会管理
exhibitor 展商管理
registration 报名审核
booth 展位资源
order 参展订单
contract 合同管理
payment 收款退款
selection 选位锁定
service-center 服务中心
invoice 发票
notification 通知
report 报表
audit 审计日志
file 文件管理
scheduler 定时任务
```

### 4.3 接口风格

后端提供 REST API。

接口约定：

- 请求和响应使用 JSON。
- 分页参数统一为 page、pageSize。
- 列表响应统一返回 records、total、page、pageSize。
- 金额字段使用字符串或定点数字格式，避免前端浮点误差。
- 状态字段返回 code 和 label，前端根据 code 渲染 Tag。
- 文件上传接口返回 fileId、fileName、fileUrl、contentType、size。
- 关键写入接口必须支持幂等，包括支付回调、选位提交、退款触发、服务申请提交等。前端或外部系统传入 requestId 或 clientToken，后端按业务对象 + 请求标识做幂等保护，重复请求不得产生重复付款、重复锁位、重复退款或重复服务申请。

### 4.4 事务边界

必须使用数据库事务的场景：

- 展位锁定。
- 选位审核通过。
- 选位驳回或超时释放。
- 选位取消。
- 财务确认收款。
- 退款完成。
- 合同变更完成。
- 展位释放待办处理。

事务内必须同时更新业务状态和写入审计日志，避免状态变化无记录。

## 5. PostgreSQL 数据库方案

### 5.1 数据库原则

- PostgreSQL 是唯一最终业务状态来源。
- PostgreSQL 实例由采购方提供并交付 JDBC 连接信息，应用方不新建数据库实例。
- 所有业务表统一部署在采购方 PostgreSQL 实例下的独立 schema 中，默认 schema 命名为 exhibitor_sys，可通过应用配置项注入覆盖。
- 应用账号仅授予该 schema 范围内的 DDL 和 DML 权限，不访问采购方实例下的其他 schema。
- 应用必须显式使用应用 schema，禁止依赖默认 public schema 或连接池会话级 search_path。
- 不进行历史数据迁移，schema 内业务表从空白启动。
- 业务表结构由应用启动时通过受控 SchemaInitializer 在应用 schema 内完成空库初始化，不使用数据库迁移工具。后续结构变更仍需形成版本化 SQL 脚本、上线审批和回滚说明，但不引入自动迁移框架。
- 核心业务表必须显式包含 event_id。
- 金额字段使用 numeric(14,2)，统计聚合查询显式 cast 为 numeric(18,2)。
- 状态字段使用受控 varchar 或字典表约束。
- 所有业务表包含 created_at、updated_at、created_by、updated_by。
- 财务、合同、审计、付款记录不允许物理删除。
- 高频查询字段建立索引。
- 状态流转只能通过服务层执行。

### 5.2 核心数据表

核心表建议：

```text

zones

registrations

price_rules
participation_orders
contracts
contract_versions

refund_payment_items

booth_selections

```

表设计补充：

- contracts 保存当前合同主记录。
- contract_versions 保存每次合同生成、签署、变更后的全量快照，包括版本号、生成原因、合同内容快照、金额、面积档位、签署状态、签署人、签署时间、合同附件 fileId、创建人和创建时间。
- 合同变更不覆盖旧版本，变更完成后生成新 contract_versions 记录，并更新 contracts 当前版本指针。
- payments 只记录付款与收款确认。
- refunds 独立记录订单级退款流程，关联 order_id，保存退款金额、状态、原因、审批与处理记录，不在 payments 中使用负数记录退款。
- refund_payment_items 记录退款与原付款记录的分摊关系，关联 refund_id、payment_id 和本次退款分摊金额。单笔退款可以分摊到多笔原付款，多笔退款也可以分别关联同一订单下的不同付款记录。
- booth_release_tasks 记录展位释放待办，状态包括待处理、已处理、已取消。
- selection_eligibilities 独立成表，用于承载选位资格状态、pause_reason 和资格变更历史，避免把选位资格逻辑塞进 participation_orders 主表。

### 5.3 展位锁定一致性

展位锁定必须由 PostgreSQL 事务保证。

处理原则：

- 同一 event_id + booth_id 同一时间只能存在一个有效锁定或确认归属。
- 创建选位申请时，后端在事务内校验所有展位状态。
- 对涉及的 booth 行使用行级锁。
- 所有所选展位必须整体成功锁定，不允许部分成功。
- 申请级锁位截止时间写入 booth_selections。
- booth_locks 继承申请级截止时间。

### 5.4 付款聚合

参展订单付款状态由付款记录聚合计算：

- 已确认付款金额合计大于或等于订单总价时，订单进入已付款。
- 已确认付款金额大于 0 且小于订单总价时，订单进入部分付款。
- 部分付款不能开放选位。
- 退款通过 refunds 表记录订单级退款流程，通过 refund_payment_items 关联一笔或多笔原付款记录。
- 已确认付款净额 = 已确认付款金额合计 - 已完成退款金额合计。
- 退款完成后根据已确认付款净额和订单状态重新计算订单付款状态，并按业务规则生成展位释放待办。
- 冲正必须关联原付款记录并写入审计日志。

### 5.5 数据归档与审计

审计日志记录：

- 操作人。

- 操作对象。

- 操作原因。
- 请求来源。

- 价格调整。
- 订单确认。
- 合同生成和变更。
- 财务确认。
- 退款和冲正。
- 选位提交。
- 选位审核。
- 选位取消。
- 选位草稿超时清理。
- 展位释放。
- 服务申请审核。

## 6. Redis 使用方案

### 6.1 Redis 职责

Redis 用于：

- 选位草稿 TTL。
- 验证码。
- 登录 token 黑名单或会话缓存。
- 热点系统参数缓存。
- 展位选择页面短期缓存。
- 辅助分布式锁。

Redis 不用于保存最终业务状态。

### 6.2 锁策略

展位正式锁定以 PostgreSQL 事务为准。

Redis 锁只用于减少并发请求冲突和重复提交，不作为唯一一致性保障。

选位提交流程：

```text
前端提交选位申请
-> 后端尝试 Redis 辅助锁
-> 进入 PostgreSQL 事务
-> 校验订单选位资格
-> 校验展位状态和面积合计
-> 行级锁定 Booth
-> 创建 BoothSelection 和 BoothLock
-> 更新 Booth 状态为锁定中
-> 写审计日志
-> 提交事务
-> 释放 Redis 辅助锁
```

### 6.3 定时任务

后端定时任务负责：

- 清理过期选位草稿。
- 处理锁位超时。
- 处理合同变更恢复后的锁位时钟续期。
- 发送锁位即将超时通知。
- 发送服务事项截止提醒。
- 处理通知补偿。
- 执行数据归档任务。

锁位超时处理必须在数据库事务内原子执行：

```text
BoothSelection -> 已超时
Booth -> 可选
SelectionEligibility -> 可选位
AuditLog -> 写入系统操作记录
```

合同变更恢复后的锁位时钟续期规则：

- 定时任务或合同变更完成事件需要识别因合同变更暂停过的待审核选位申请。
- 若变更完成后原申请继续有效，按暂停前剩余锁位时间重新计算锁位截止时间。
- 若变更导致面积或展区规则变化，取消原待审核申请并释放关联展位。

## 8. 权限与安全方案

### 8.1 认证与授权

系统采用 RBAC 权限模型。

权限维度：

- 用户。
- 角色。
- 菜单权限。
- 按钮权限。
- 数据权限。

角色包括：

```text
展商账号
系统管理员
主办方管理员
招商销售人员
展位规划人员
财务人员
服务中心人员
```

### 8.2 数据权限

数据权限按角色控制：

- 展商只能访问自己的报名、订单、合同、付款、选位和服务数据。
- 销售可访问自己跟进的展商数据；是否可看全部展商由系统参数控制。
- 财务可访问订单付款、服务订单付款、退款、发票数据。
- 服务中心人员可访问服务申请和服务订单。
- 系统管理员主要负责技术运维，不默认作为业务审批人。

### 8.3 安全控制

- 登录失败次数限制。
- 密码加密存储。
- 接口鉴权。
- 文件访问鉴权。
- 关键操作二次确认。
- 财务操作强审计。
- 合同、付款、退款、展位释放不可物理删除。
- 敏感配置通过环境变量或配置中心注入。

## 9. 关键业务实现方案

### 9.1 选位资格

SelectionEligibility 状态：

```text
未开放
可选位
暂停中
已关闭
```

规则：

- 未付款订单保持未开放。
- 已付款订单进入可选位。
- 草稿不暂停选位资格。
- 提交待审核申请后进入暂停中。
- 暂停中必须记录 pause_reason。
- 退款完成、合同作废或订单作废后进入已关闭。

### 9.2 选位申请

BoothSelection 状态：

```text
草稿
待审核
已确认
已驳回
已超时
已取消
```

规则：

- 草稿不锁位，默认 24 小时 TTL。
- 待审核才锁定展位。
- 已确认选位不能直接取消，必须走展位释放待办。
- 草稿和待审核可取消。
- 同一订单同一时间只能有一个草稿或待审核申请。

### 9.3 展位状态同步

展位运行状态：

```text
可选
锁定中
已确认
预留
禁用
```

同步规则：

- 选位申请提交后，关联展位从可选变为锁定中。
- 审核通过后，关联展位从锁定中变为已确认。
- 审核驳回、超时、取消后，关联展位从锁定中恢复为可选。
- 已确认展位释放必须走后台释放待办。

### 9.4 合同变更

合同变更中期间：

- 冻结付款。
- 冻结选位。
- 冻结展位释放。
- 待审核选位申请暂停审核。
- 锁位截止时间暂停计时。

变更完成后：

- 若面积和展区未变化，恢复审核并继续剩余锁位时间。
- 若面积或展区变化，取消原待审核申请，展位恢复可选，订单重新计算选位资格。
- 若新合同金额低于已确认付款金额，财务先处理差额退款。

### 9.5 退款与展位释放

退款完成后：

- 订单进入已退款。
- 选位资格进入已关闭。
- 若存在已确认展位，系统生成展位释放待办。
- 系统不自动释放已确认展位。
- 管理员或有权限人员处理释放待办后，展位恢复可选。

### 9.6 服务中心

服务事项支持配置：

- 开放条件。
- 办理粒度。
- 截止时间。
- 必填字段。
- 必传附件。
- 是否收费。
- 审核流程。

办理粒度：

- 按订单办理。
- 按展位办理。

收费服务生成独立 ServiceOrder。ServiceOrder 不参与参展订单选位资格计算。

## 10. 部署与运维方案

### 10.1 部署拓扑

```text
Nginx
  -> 前端静态资源
  -> /api 反向代理到 Spring Boot

Spring Boot
  -> PostgreSQL（采购方提供实例，应用使用独立 schema）
  -> Redis
  -> 文件存储
```

PostgreSQL 由采购方提供并维护实例。采购方负责交付 JDBC URL、连接账号和访问网络。应用方在采购方实例下使用独立 schema 部署业务表，不参与实例级运维。

### 10.2 环境划分

建议至少提供：

- 开发环境。
- 测试环境。
- 预生产环境。
- 生产环境。

不同环境使用独立 PostgreSQL 实例或独立 schema、独立 Redis、独立文件存储路径和独立配置。生产环境的 PostgreSQL 实例由采购方提供，开发和测试环境数据库可由应用方自建或由采购方提供测试 schema。

### 10.3 日志与监控

日志包括：

- 应用日志。
- 访问日志。
- 错误日志。
- 审计日志。
- 定时任务日志。

生产环境日志可先落盘，后续接入 ELK 或其他日志平台。

### 10.4 备份策略

PostgreSQL 数据库的实例级备份由采购方负责，包括全量备份、WAL 归档、恢复策略和恢复演练。应用方不直接执行数据库级备份。

应用方负责的备份相关交付：

- 提供针对应用 schema 的 pg_dump 备份脚本和恢复脚本，由采购方按其备份周期纳入执行。
- 提供 schema 范围内的备份对象清单，便于采购方按 schema 维度做选择性恢复。
- 文件存储定期备份，由应用方按部署形态执行。
- Redis 根据使用场景开启 RDB 或 AOF，由应用方维护；Redis 中不保存最终业务状态，丢失只影响草稿和缓存。
- 应用方定期参与采购方组织的备份恢复演练，验证 schema 级恢复流程可用。

## 12. 与业务设计的对应关系

本技术方案对应业务设计文档：

```text
docs/superpowers/specs/2026-06-12-exhibitor-system-production-design.md
```

业务设计中的关键约束在技术方案中对应如下：

- 财务确认后才能选位：通过 ParticipationOrder 付款聚合和 SelectionEligibility 实现。
- 展位不重复销售：通过 PostgreSQL 事务、行级锁和 BoothLock 实现。
- 选位草稿 TTL：通过 Redis TTL 和后端定时清理实现。
- 退款不自动释放已确认展位：通过展位释放待办实现。
- 服务中心按条件开放：通过 ServiceItem 开放条件和办理粒度配置实现。
- 页面严格遵守 Ant Design：通过 Ant Design + ProComponents 组件规范实现。
- 技术方案补充了业务设计未单独列出的展位释放待办和服务订单管理页面，后续修订业务设计文档时应同步纳入。
- 数据库部署形态：采购方提供 PostgreSQL JDBC，应用在该实例下使用独立 schema 部署业务表，新系统空白启动；对应业务设计 §13.1 的数据库部署方式默认方案。
